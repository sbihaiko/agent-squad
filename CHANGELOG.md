# Changelog

## 0.2.30 (local fork, 2026-10-11)
- **#1785 — the acceptance-command cap no longer kills the check the instructions name.** `squad/workcmd.py` ran every `ac_command` under `TIMEOUT_S = 120`, while the fork's own canonical check `contrib/squad-goal/scripts/shell-suites.sh` runs the 41 `test-*.sh` suites next to it and took 158.69 s real on an idle machine (234 s on a loaded one). Run `run-20261011-132053-54d24b` recorded `ac_failed:timeout after 120 s` twice — for `~/wt-as-1767` (#1767) and `~/wt-as-1768` (#1768), the only two children of seven that did not land — with both commands exiting 0 by hand, and the run's `verdict` was `failed`. `TIMEOUT_S` is now 300 s, `ac_timeout()` reads `SG_AC_TIMEOUT` (a value that is not a positive number keeps the default, so a mistyped knob never kills every command), and `run()` resolves the cap at call time so the gate and the landing check both honour it; a timeout still records `ac_failed:timeout after <the value it used> s`. The router prompt (`prompts/router.md`, seeded as `docs/design/router.graph.json`) no longer points at "the project's test command" as the default: it asks for the narrowest command that proves the done condition and names the cap, and `contrib/squad-goal/SKILL.md` says so for fork-only children.
  - `tests/test_workcmd.py`: the default clears 300 s and `SG_AC_TIMEOUT` moves it (junk and zero keep the default); a run honours the configured cap and reports `timeout after 0.2 s` with `malformed` false, so a killed command never reads as a syntax error.
- **#1770 — a refused fix dispatch no longer keeps the head queued.** `autopilot.sh` touches `auto/queued-<pr>-<sha9>` before it calls `autofix.sh` and skips the head while that marker exists, and `autofix.sh` charged the round before it built the request, so a request `mkreq.sh` refused left the head queued forever with the round of a dispatch that never happened spent against its cap — PR #1706 @ `27aaaf5b5` kept a BLOCKING verdict, green CI and no fix run until a human pushed. The refusal now frees the `fix-` and `queued-<pr>-<sha9>` markers it wrote, drops the `rounds-`/`softfix-<pr>` line it charged, and exits 75 so a caller can tell the refusal from a failed run; the next pass retries the head. That is the shape #1529 gave `autobug.sh` and `autofrontier.sh`.
  - `test-autofix.sh` gains case 5 (a refused dispatch: no `queued-`/`fix-` marker, no round, no run, exit 75) and case 6 (a dispatched fix keeps the marker and the round).
- **#1513 — a dispatch that ends without work no longer strands its issue.** Twelve cards (#1492 … #1510) sat `In Progress` with their `auto/disp-<n>` / `auto/bug-<n>` markers in place while their runs had already ended (`adapter_error`, `node_spend_cap`): `autofrontier.sh` and `autobug.sh` move the card before the run starts and nothing undid it, and rule E sweeps only a `disp-` marker whose request log happens to say `verdict failed`. The janitor gains rule O — a run whose record ends with `verdict: failed` and holds no `land` pass released every issue of its request (marker `auto/disp-<n>`/`auto/bug-<n>` dropped, card back to `Todo` on the loop board and to `To triage` on `$SG_BUG_PROJECT`), so the next cycle dispatches it again. The card moves only while it still sits in the column the dispatch set (`In Progress` / `$SG_BUG_DOING`), so a card another step moved past it is never downgraded, and a run that landed work, an issue a live run works, or an issue a PR names keep their card and their marker. Once per run; the queued comment carries the run id and the verdict's reasons.
  - New `contrib/squad-goal/scripts/test-janitor-failed-dispatch.sh`.
- **#1512 — a provider outage no longer ends a run at its first model.** Five dispatches on 2026-10-11 died in about three seconds each with `adapter_error` and $0.00 spend, all carrying `API Error: 402 Grok upstream rejected the request`: the exhausted provider was the *first* entry of the chain, and the first `adapter_error` ended the node. `squad/session.py` gains the chain rule — `model_chain(models, first)` (the model the node or the request picked leads the dispatch envelope's `allow.models`), `provider_error(err)` (an adapter error whose text names an upstream HTTP status: any 4xx/5xx under `API Error`/`upstream`/`"status"`), and `chain_message(tried)` — and both runners walk it: `runners/agent.py` for an agent node, the router entry included, and `runners/children.py` for a dispatch child, which retries in the same worktree (the tree is cut once, the retry says so in its own `call_start`). An error that names no provider status still fails the node at once, and a chain of one keeps its own error. A chain whose every entry refuses fails once, with `reasons: ["adapter_error"]` and one `diagnostic.error` naming each entry and its error ("every model in the chain failed: opus (…); sonnet (…); haiku (…)"), so the hub shows the whole outage in one line instead of the last refusal. The model an outcome names is the one that answered, not the one the request named first.
  - New `tests/test_model_fallthrough.py`: a 402 on the router falls through to the next `allow.models` entry; the same on a child falls through in the child's own worktree; the 402 also reads from a bridge log line (`"status": 402`, no `API Error` prefix); an exhausted chain fails once naming all three entries and their errors; and "socket closed" still fails at once on the first model.

## 0.2.20 (local fork, 2026-10-10)
- **A conflicted head is not reviewed.** `autopilot.sh` now asks for `mergeable_state` before it starts a review. A head that conflicts with its base will move before it can merge, so reviewing it spends a model on a diff that is about to change, and the conflict round that follows pushes a new head which is then reviewed a second time. The conflict goes first — `autofix.sh` already knows that problem — and the review sees the rebased head. PR #1285 was reviewed, and approved, against a head that had been doomed for minutes, because its sibling #1391 had merged on top of the same files.
- **`mkreq.sh` warns about overlapping slices.** A panel's children are meant to hold disjoint file slices, and a request already names the files it will touch. When one names a file an open PR is already changing, or that another queued request claims, the slice guard appends a `SLICE NOTE` to the request and prints `SLICE WARNING` on stderr. It warns, never blocks; the guard loads the profile in a subshell, so a checkout with no matching profile simply skips the open-PR half instead of failing the launch.

## 0.2.19 (local fork, 2026-10-10)
- **The review chain is ordered by what it measures.** `review_models` now opens with `gemini-3.8-flash-high` (30 tries, 0 failures, p50 26 s), then `claude:claude-opus-5-5` (26 failures in 57, p50 38 s), then `grok-4.5` (35 failures, p50 188 s), and `gemini-3.8-flash-medium` last — that is the entry that most often spends the account-wide `agy` quota and so takes the whole gemini family down with it. The old order opened with a model that is outside its `hours` window for twelve hours a day, and kept the reliable one as a fallback.
- **Age SLA in `autopilot.sh`.** The loop records each PR's own birth (`auto/seen-<pr>` holds the epoch of its `created_at`), so the age is the PR's and not the moment the loop happened to notice it. A PR open past `SG_AGE_MINUTES` (30) leads the queue — the open-PR list is sorted oldest-first instead of taking the API's order — and its review runs on a short leash: `SG_REVIEW_CHAIN_DEPTH=1` model, `SG_REVIEW_RETRY_BUDGET=1` try, `SG_REVIEW_TIMEOUT=120` s. A PR that has already waited half an hour may not spend the whole chain again while a fresh one waits behind it. `AGING` fires once per PR and `STALLED` every 15 minutes, so a stuck PR is visible in `watch.log`. The depth counts only models that are actually tried, so a chain whose head is out of quota still falls through to the next entry instead of ending `BLOCKED` untried.
- **Why:** measured over the day, 117 review attempts failed after burning their whole timeout — 273 minutes against 177 minutes of reviews that answered. A chain that opens with the model that measures best removes most of that.
- **Hub:** the `cost & speed` panel lists the open PRs with their age, oldest first, in warning colour past 30 minutes — the same threshold the SLA uses, so a stalled PR is visible without reading `watch.log`.

- **contrib/squad-goal**: the autonomous delivery loop that drives tracker issues through agent-squad
  (one `squad start` per frontier, live issue comments and board, independent review, autopilot, hub).
  Synced from the working skill with `scripts/sync-to-fork.sh`; per-repo profiles stay local, and
  `scripts/profiles/example.sh` is the template. Needs `gh`, and `drive-board`'s `board-status.sh` for
  board moves. Highlights:
  - **Autopilot** (`autopilot.sh`, every 30 s from `watch.sh`): reviews each new PR head, then
    `autofix.sh` sends CHANGES, failed CI, conflicts and unresolved review threads back to the squad as
    one fix run (2 rounds; thread- or conflict-only rounds have their own cap of 3); at the cap,
    `autopanel.sh` asks a panel model for one more round or labels the PR `needs-human`; merges on
    APPROVE + green CI + clean + no unresolved threads.
  - **Review** (`review.sh`): walks `review_models` with a per-model timeout (`review_timeout_seconds`),
    logs latency to `review-times.tsv`, and reviews fix rounds on the delta since the last reviewed sha
    with the previous findings (full review on a first pass, a rebase or a big delta).
  - **Optimistic stacking**: `stack.sh` lets an issue start on its only open blocker's PR branch (one level, parent CI not red); the autopilot holds the stacked PR until the parent merges, then retargets it to the base branch and fixes the squash conflict with `rebase --onto`; its review covers only its own diff over the parent.
  - **Done check**: every request asks the child for `ac_commands` (wrapped in `acpr.sh <branch> -- <cmd>` for PR-branch work, since the final gate runs in the main checkout), so `ac-verify` verifies instead of failing with `no_ac_commands`; the hub shows a landed run with nothing verified as `unverified`, in its own color.
  - **Worktrees**: `wtclean.sh` removes finished, pushed child worktrees and leaves the run folder and its dashboard server alone (the hub lists runs from live servers); unpushed ones are kept and reported.
  - **Issue comments**: dispatch, PR opened, run verdict, review/CI result, fix, panel, merge and e2e are
    queued and posted on the issue by `cqflush.sh`.
  - **Hub** (`hub.py`): live run dashboards, board columns with live totals (closed PRs counted from the
    real total), PR open-age pill, auto-selection of a new run, readable run names; repo and board come
    from the profile.
