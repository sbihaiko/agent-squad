# ADR-0162: The hub writes the loop switch, drains by default, and the tailnet reads it unless granted

## Status

Accepted, on one condition: tailnet writes stay off by default, and only the owner turns them on. [ADR-0152](0152-reach-the-web-surfaces-over-the-tailnet.md), rule 9, holds the tailnet side of this decision.

## Context

The owner starts and stops the loop from the hub. The hub has read the loop state only, and a stop kills every live run and gate at once. A run and a gate that stop mid-work leave a branch, a lock and a record to recover. The tailnet reaches the hub through one rule ([ADR-0152](0152-reach-the-web-surfaces-over-the-tailnet.md)), and a write from it needs its own grant, as the phone's session send does ([ADR-0154](0154-the-phone-sends-to-a-session-by-the-wire-protocol.md)).

## Decision

1. **One route.** The hub serves `GET /api/loop`, which returns the state, who changed it and when, the live runs and gates, the change log, whether this request may write, with the reason when it may not, and the actions the state allows. The hub holds that rule, so no page does. `POST /api/loop` takes a JSON body with one action: `start`, `drain` or `stop-now`. The route refuses, with 409, an action the current state does not allow. The route runs the supervisor script, and a stop-now also ends the listed runs and gates.
2. **Four states.** `on` and `draining` are read from the live supervisor and its drain mark. `starting` holds only while a hub start is in progress: the route writes a pending mark before it runs the supervisor script and removes it when the script returns. `off` is every other case. A start that fails, or whose supervisor is not alive after it, reads `off` and the view shows the failure. Only the route and the supervisor write them.
3. **Drain is the default.** A drain pauses dispatch and marks itself. The pause is the drain's own: every start lifts it, from the hub or the terminal. A start during a drain also cancels it: its waiter ends, so the loop stays up when the work ends. A pause the owner set before the drain stays. A detached waiter stops the loop only when no run is live and no gate lock holds a live pid. A run is live while it has no verdict and its process runs: the pid of its last `call_start` is alive as a squad run, or, before its first call, its record moved in the launch window. A run that died with no verdict never holds the drain. A drain never sends a stop while live work remains, and a supervisor that dies during a drain ends the waiter.
   A restart after a publish is this drain and then a start (`watchd.sh restart`): a publish reaches the drivers only through a restart, and a stop under a live run kills the run and its gate. The lanes keep their beat under the pause, so the takeover bound still ends a stuck run, and the restart follows that verdict. A plain drain is a stop the owner asked for: a restart that finds one refuses and names it, never turning the stop into a restarted loop. With the loop already down, a restart only starts it.
4. **Stop-now is the second choice.** It needs `"confirm": true`. Its confirm lists the live runs and gates it kills. A run starts in its own session, so the supervisor's stop does not reach it: the route ends each listed run (the process its record names, only while that process is a squad run and not the hub) and each held gate, with its process tree. Each run it ends gets its killed verdict at once, through `squad.killed`. Its response and audit line name what died, and name what it could not end as survived.
5. **Audit.** Every change the route runs appends one line to the loop audit file in the state directory: who, when, from where (loopback or tailnet), the action and, for a stop-now, what it killed. A refused request writes nothing. The loop is the second writer: a drain it starts for an open loop-bug and the start that follows the close each append one line, `who` `loop`, `from` the pass, with the issue number (ADR-0146). The page shows both with the issue.
6. **Tailnet.** A tailnet request may read the route. A write from the tailnet is refused, with its reason, unless the profile sets `tailnet.loop_write` (`SQUAD_TAILNET_LOOP_WRITE`) to true. The shipped default is false, and only the owner sets it. The grant holds for every allowed login of the profile, as `tailnet.terminals_send` does.
7. **Three places show one view.** The Monitor card, the Loop tab and the phone's Loops page read the same route. The Monitor card and the phone show the state beside the switch; the Loop tab and the phone show the change log, with who changed the state and when. Settings has no Loop theme. The switch has no Save: a change is one request. The reason a tailnet request is read-only is shown beside the switch, with a failed start's reason until a later start runs, and Settings > Access shows the tailnet rule itself.
