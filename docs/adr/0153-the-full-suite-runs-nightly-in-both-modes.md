# ADR-0153: The full suite runs nightly in both modes, in its own tree and lock

## Status

Accepted. The nightly runs in one hour of the day and is split between GitHub and the machine, with one verdict.

## Context

Every gate the loop runs is bounded by time. The fast battery that a work-branch tip and a wave entry run deselects `heavy`, runs one mode and runs only the test files its diff reaches, so the calls it skips, the two-mode difference and the files it does not reach go unchecked until the complete CI tier runs on the `stg` tip ([ADR-0173](0173-the-complete-tier-runs-on-the-promotion-request.md)); its result line says which files it ran, or that it ran all. The promotion proof runs the full suite in both modes, but only when the owner starts it, and it holds the landing lock while it runs, so no wave lands meanwhile ([ADR-0145](0145-a-work-branch-lands-in-dev-by-fast-forward.md) rule 3).

A defect that only a heavy call or a serial run shows can therefore sit in the landing branch for days, and the reader of the hub has no reading of it at all.

## Decision

1. **The full suite runs nightly, in both modes, heavy included, split in two halves.** The GitHub half (rule 1c) runs every test a Linux runner runs. The local half runs the rest: `nightly.sh` runs `pytest -p no:deepeval -n auto` and then `pytest -p no:deepeval -p no:xdist`, with no `-m 'not heavy'`, and with `SQUAD_NIGHTLY_LOCAL_HALF=1`. That switch keeps only the tests a Linux runner deselects by marker, the macOS-bound shell suites among them. The conftest reads them from its one deselection rule with the CI runner switch on ([ADR-0139](0139-a-test-without-its-fixture-repo-is-deselected.md)), so no second list exists. A local half that passed ran only part of the suite, so the GitHub half's result at the same sha answers a `pytest` proof obligation. With no such result yet, the obligation stays in place for a later nightly, and no full suite runs locally for it. A local red still answers it red. The live check runs after the local half. The watch cycle starts it detached, once a day, under its own single-flight stage; a later cycle the same day runs nothing. It starts only in the hour the profile sets (`SG_NIGHTLY_HOUR`, 04 by default, America/Sao_Paulo). Outside that hour it never starts, also when the loop is idle.
1a. **The dispatch drains before the hour and yields to it.** From `SG_NIGHTLY_DRAIN_MINUTES` (40) before the hour, the dispatch starts no run (`gh_dispatch_hold`), so the live runs end before the hour opens. In the hour, the dispatch starts no run while the nightly runs, or until the nightly has run that day. The hold ends when the day has its nightly record or its missed record. It also ends when the time left in the hour is shorter than the suite needs (`SG_NIGHTLY_NEED_MINUTES`, 45), and the nightly does not start then: a suite that cannot finish only ends bounded, so the dispatch never idles for it. The hold ends with the hour in any case. A nightly whose verdict names a bounded local half proved nothing, so it costs the dispatch nothing: the next window holds no dispatch, and one line in `cycle.log` names that reason.
1b. **A nightly that is not finished by the hour's end records one bounded attempt.** A run still going at the hour's end is stopped there, and it records one bounded attempt. An hour that closes with no run gets one bounded record from the first cycle after it; a 23:00 hour closes at midnight, so that record is written on the next day. No later cycle repeats either record. The record is a report, never a hold.
1c. **The GitHub half is a schedule.** `.github/workflows/nightly.yml` runs the complete Linux suite on the `dev` tip, on a schedule only, with a read-only token. Each shard job runs the command of its complete-tier sibling in `ci.yml`. One job reads the `dev` tip once, and every shard checks out that one sha, because `dev` moves between two checkouts. That job uploads an artifact named `nightly-dev-sha-<sha>`, so a reader gets the tested sha with no download. A schedule is not a branch push, so the no-push rule of CI holds.
1d. **One verdict combines the two halves on one sha.** The local half runs on the sha that the day's GitHub run tested, and on the `dev` tip when no such run exists yet. `nightly.sh` writes `nightly-verdict`: the time, the verdict, the sha, the local result, the GitHub result and the GitHub sha. It reads the scheduled run whose artifact names the local sha, never the latest run, through the gh door (`ghcall.sh`). A run of an earlier day never answers the verdict. Fail in either half is fail. Pass in both halves on the same sha is pass. Any other pair is unproven: a half that is missing, unfinished, bounded, or at another sha. The verdict is written after each local run. A later call reads it again while it is unproven, at most once per `SG_NIGHTLY_VERDICT_EVERY` seconds and for one day after the local record, so a GitHub half that ends after the local half still settles it. A GitHub-half red is a red like a local one (rule 6): one alert by the same path, once per sha, and one dispatch note, once per verdict. It is a report, never a hold.
2. **It runs in its own tree.** The suite runs in a plain clone at the state directory, never in the owner's checkout and never in a child's worktree, so no suite it runs can touch the line the loop is working on. It is not a `~/wt-*` worktree, so the worktree cleanup never removes it.
3. **It takes its own lock and never the landing lock.** Its serial name is `nightly`, in try mode, so a second start never queues behind a suite of hours. It never takes the `gate` lock that the landing gate, the wave entry and the promotion wait on, and a nightly in flight never delays a landing; a held landing lock holds the nightly before it starts (rule 7).
4. **One result record is the nightly's only output.** The record is written by a temp file and a rename ([ADR-0030](0030-atomic-writes.md)) and holds the time, the result, the sha, each mode's own result and the failing test ids. The result is a pass only when both modes pass. The two mode logs stay beside it.
5. **The hub draws the record as one fact.** The footer reads the record and the verdict (rule 1d): a local pass shows as pass only when the verdict at its sha is pass, and as unproven otherwise. The footer shows the result and its age, in the error tone when the suite is red, with each mode's result, the sha and the failing tests on the hover. A record the hub cannot read is a question mark, never a pass.
6. **A red result alerts once and is a report, never a hold.** The alert takes the path `health.sh` already uses: one line in the alerts file and one notification. The dispatch hold both dispatch passes read says the note once per record and the pass goes on: each landing carries its own local fast gate, and the promotion still needs its own proof ([ADR-0173](0173-the-complete-tier-runs-on-the-promotion-request.md)). The hold compares the record's sha with the dev tip: a record whose sha is another commit is red for a base the tip no longer is, so the tip is unproven and not red, and the note names both shas. A missing or unreadable record never holds, and neither does a record whose sha the checkout does not carry: the loop is never blocked on a file it cannot trust.
7. **It holds while a run is live or the gate lock is held.** A full suite beside live runs and their gates saturates the box and bounds every gate, so the suite waits for them inside its hour while the dispatch stays stopped, and the live runs end. The drain lead of rule 1a stops the dispatch before the hour, so most runs end before it opens. A run is live by the one reader the drain and the hub use (`squad/run_liveness.py`): a run with no verdict whose engine pid still runs, or, before its first call, whose record moved within the launch window. Only an `idle` answer lets the suite start; a reader that cannot answer holds it. The gate lock holds while its pid lives. A held start writes no day marker. A nightly that follows a bounded one shares the machine instead: it starts beside the live runs and a held gate lock, because a bounded suite proved nothing, and a second idle night proves no more than the first.

## Consequences

A defect that only the heavy or serial mode shows now surfaces within a day, whatever the promotion to `main` waits for, and the hub names the tests that failed.

A full suite no longer runs beside a busy loop, so a child's gate keeps its bound. The cost is the drain lead and the start of the hour: at most `SG_NIGHTLY_DRAIN_MINUTES` plus 60 minus `SG_NIGHTLY_NEED_MINUTES` of held dispatch a day. When a live run outlasts the drain, the day has one missed record and no nightly, and the dispatch resumes once the suite can no longer finish, not at the hour's end.

A tip the nightly has not seen is delivered on, unproven, until the next nightly proves it. The risk is bounded to one nightly: a defect that only a heavy call shows can land before the nightly names it, and the red record then holds the next tip.

The machine spends the local half once a day, and GitHub spends the rest. The GitHub half starts only from the workflow file on the default branch, so it runs after the file reaches `main`. It never adds a gate, so no entry and no landing becomes slower.

## Guard

`contrib/squad-goal/scripts/test-nightly.sh` guards rules 1 to 4, 6 and 7 (both modes in the nightly tree, the record, the alert, the lock names, the day marker, the dispatch hold and the holds for live runs and the gate lock). `contrib/squad-goal/scripts/test-watch-cycle.sh` (case 12) guards rule 1 (the cycle starts the suite detached and does not wait for it). The window, the dispatch hold and the bounded attempt of rules 1, 1a and 1b are guarded by the window cases of `contrib/squad-goal/scripts/test-nightly.sh`. `tests/test_tooling.py` guards rule 1c (the schedule trigger and no push trigger, the dev ref and the one sha, the artifact, the shard commands and the read-only token). `tests/test_ci_runner_switch.py` guards the local-half selection of rule 1. The default local-half commands and the verdict table of rule 1d are guarded by the local-half and verdict cases of `contrib/squad-goal/scripts/test-nightly.sh`. `tests/test_hub_nightly_fact.py` guards rule 5 (the fact, the modes, the sha and the failing tests).
