# ADR-0145: A work branch lands in `dev` by a fast-forward push, with no pull request

## Status

Accepted (owner). Decision, verbatim: "three long-lived branches (`dev`, `stg`, `main`); a work branch lands in `dev` by a fast-forward push, with no pull request; the loop promotes `dev` to `stg` when the CI of the `dev` tip is green; the owner promotes `stg` to `main` with one command; the live copy publishes from `stg`; a card is Done when its branch is in `dev`."

Amended (owner, after a Fable review). Decision, verbatim: "ADR-0145 gains the wave rules approved by the owner after a Fable review: one branch per wave; a child enters it by a rebase on the wave tip and `--ff-only`, after its local gates pass in its own worktree; a child that fails never enters; the CI runs once per wave, when the wave lands in `dev`; a red wave CI finds its cause by running each child's suite again against the wave tip, the last entrant first; a wave has an age cap; Code Complete means the child is in the wave branch, Done means the wave is in `dev`; the wave branch is rebased on `dev` only before the final push."

Amended (owner). Decision, verbatim: "Rewrite ADR-0145 rule 3 in place, and the watch.sh comment with it."

## Context

A pull request per work branch put a review step and a CI queue between finished work and the rest of the work. The repository is private and the suite is the check ([ADR-0116](0116-implement-in-a-worktree.md)), so the step added latency and no evidence. One `main` also served three jobs: the line work lands on, the line the live copy publishes from, and the line the owner trusts. A landing that was not yet trusted could still reach the live copy.

## Decision

1. **There are three long-lived branches: `dev`, `stg` and `main`.** Every other branch is a work branch and ends when its work lands.
2. **A work branch lands in `dev` by a fast-forward push, with no pull request.** The run rebases its branch on `origin/dev`, runs its checks, and pushes the tip to `dev`. A rejected push repeats from the fetch. A run never force-pushes a long-lived branch. A kept landing branch whose tip `origin/dev` already carries has landed in an earlier round: the pass writes its books — the landed fact, the closes, the cards — and removes the branch, its wave branch and its marker, with no review, no gate and no push. An ordinary work branch at the base tip is not that case: it carries no commit yet and waits for its review as before.
3. **The loop promotes `dev` to `stg` on the proof of the `dev` tip, and `stg` to `main` on the complete tier of a `stg` sha.** The first owner decision is recorded verbatim in [ADR-0143](0143-a-card-only-moves-forward.md): "the loop promotes `dev` to `stg` when the CI of the `dev` tip is green; the owner promotes `stg` to `main`". The owner later gave the second step to the loop ([ADR-0173](0173-the-complete-tier-runs-on-the-promotion-request.md)). The watch cycle carries the promotion step: it runs `promote-pass.sh` under its own single-flight lock, so two cycles never overlap a pass, and detached, so a pass in flight costs the cycle nothing. The step has its own debounce: it starts only when the latest landing is older than the quiet window, so a burst of landings earns one proof window rather than one pass per landing. The wait is bounded: a stream of landings that never quiets postpones the proof by the deferral bound (twice the quiet window unless the profile names another) and no longer. The proof is the green fast tier of that tip (`SG_PROMOTE_PROOF=ci`, the cycle's setting; [ADR-0173](0173-the-complete-tier-runs-on-the-promotion-request.md)), or a full local suite in both modes that the command ran at that exact tip (`SG_PROMOTE_PROOF=local`). A CI proof is a job on the runner, so it runs no local suite, and a loaded box or a nightly that owns the machine refuses it nothing ([ADR-0164](0164-delivery-outranks-the-proof.md)). A local proof runs in its own tree under its own proof lock, as the nightly does ([ADR-0153](0153-the-full-suite-runs-nightly-in-both-modes.md)). Neither proof takes the `gate` lock, which the landing gate, the wave entry and the promotion wait on, so no wave waits on a proof. The consolidation is one pull request (owner rule, every project): the command opens or reuses the open `dev` → `stg` pull request and merges it with a merge commit, and no script pushes `stg`. That merge runs through `promote-stg.sh`, which holds the `gate` lock as every promotion does, for one pull-request merge and never for a suite. A red or missing proof promotes nothing, the pull request stays open, and a later proven tip carries the earlier work with it. A red tip holds the promotion: the loop fixes the tip, and never promotes around it.
4. **`main` moves by a fast-forward, never by a merge.** The loop's stg-to-main pass moves `main` to the `stg` sha whose complete CI tier is green, through `promote-main.sh <sha>`; it is the one script that pushes `main` ([ADR-0173](0173-the-complete-tier-runs-on-the-promotion-request.md)). The owner keeps the same command: with no argument it fast-forwards `main` to the `stg` tip.
5. **The live copy publishes from `stg`.** It never publishes from `dev` or from a work branch ([ADR-0140](0140-the-live-copy-follows-in-the-cycle.md)).
6. **A card is Done when its work is in `dev`.** A pull request no longer exists to carry the landing, so the landing is the tip reaching `dev` ([ADR-0143](0143-a-card-only-moves-forward.md)). For a child in a wave, rule 12 sets the meaning.
7. **CI runs on the `dev` → `stg` pull request,** so the one run that moves `stg` carries its own evidence.
8. **A wave has one branch.** A wave is the set of children that land in `dev` together. The wave branch is the only branch that lands in `dev` for them.
9. **A child enters the wave by a rebase on the wave tip and `--ff-only`,** wherever its worktree was cut: the rebase at entry places its commits on the wave, so no rule cuts the worktree from the wave branch. It enters after its local gates pass in its own worktree and after the review of its own commits approved them. A child of the loop is reviewed by its own run: the loop workflow's review gate runs `runreview.sh` in the child's worktree before the run merges it, and the entry then reads that review and asks for no second one. The review of a run child is read in the child's own worktree, against the wave branch: a child pushes no branch of its own, so no review of a pushed branch can see it. A run with no wave answers "no review here", and the child-completion pass reviews the child later; so do the children of runs that started before the review gate. A child whose review asks for changes is fixed by its run, in its own worktree, while each round changes the findings (ADR-0134). A child whose fix rounds stall, whose review said BLOCKED, or whose next round the run cannot fund never enters the wave: its run holds it, its issue goes back to the queue with every blocking finding, and it is requeued once. A child that fails its gates never enters the wave either; its issue goes back to the queue. A child the entry holds (no review, a wrong base, a lock held) stays out without a requeue, and the wave waits for it; repeated holds on one head requeue it.
10. **CI runs once per wave, when the wave lands in `dev`.** A child's entry into the wave starts no CI of its own.
11. **A red wave CI finds its cause by running each child's suite again against the wave tip, the last entrant first.** The first suite that fails names the child that broke the wave. A wave with nothing ahead of the base lands empty and runs no check: it carries no child commit that a red check could blame. It still delivers each issue whose child entered it.
12. **Code Complete means the child is in the wave branch; Done means the wave is in `dev`.**
13. **A wave has an age cap, and the cap keeps the work it can.** A wave that reaches the cap lands as it is; it takes no new child, except one whose review already approved its current head against the wave: that child waited on the loop's queue, not on its own work. The age counts no time a child waits for a gate slot: that wait is the machine's resource, not the child's work (ADR-0166). A child the cap ends with commits keeps them: the cap pushes its head to `fix/<n>-salvage-<run>`, the work branch a finished run with no wave already pushes, so the review of a work branch carries it and the landing lands it, and the frontier starts no run for the issue while that branch is open. A child with no commit sends its issue back to the queue, as before. A requeue the cap makes is no failure of the child, so it never counts toward the requeue cap. Nor does a requeue the loop caused: it counts in its own ledger, with its own larger cap.
14. **The wave branch is rebased on `dev` only before the final push.** Between entries the wave tip moves only by child entries.
15. **A burn over the token cap is a report, never a stop.** The loop writes a report line and one alert, and goes on. Other guards already bound spend: the per-call caps, the run spend cap, the weekly reserve and the quota markers. A stop on one short burst cost hours of no dispatch until the owner restarted the loop. Dispatch pauses only on a sustained runaway: the burn of the last hour, measured over one full hour, is over 3x the cap's hourly share. It resumes by itself on the first pass whose hourly burn is under that share; no owner restart is needed.

Rejected: a pull request per work branch. Rejected: a merge commit on promotion. A fast-forward keeps one line in `git log`.

## Consequences

- A change in `dev` is not yet trusted. Trust grows along the line: the fast tier of its tip moves it to `stg`, and the complete tier moves it to `main`.
- A defect that reaches `dev` is found by the CI of the `dev` tip, before `stg` carries it.

Rules 1, 4, 5, 6, 8, 10 and 14 have no guard yet; they are a draft ([ADR-0018](0018-failing-gate-is-a-defect.md)).
